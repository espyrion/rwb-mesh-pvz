# Экономическая модель

Документ описывает, что и как считается в прототипе, какие допущения приняты и где границы модели.
Числовые расчёты — в [ECON_REPORT.md](ECON_REPORT.md) (генерируется из модели, не правится руками).
Источник параметров — `economics/params.yaml`.

> **Дисклеймер.** Тарифы, бонусы, штрафы и SLA — элементы предложенной командой
> модели. Они не являются действующими тарифами RWB или его партнёров. Данные синтетические.
> Лимиты ответственности за утрату/порчу в модель не включены, вынесены в этап 0 пилота
> ([REPLICATION.md](REPLICATION.md)).

## 1. Четыре стороны

Каждый заказ описывается с точки зрения четырёх участников:

| Сторона | Доходы | Затраты |
|---|---|---|
| ПВЗ | плата за выдачу (25 ₽), хранение (5 ₽/ячейка·день), бонус за заказ без хаба (15 ₽) | приёмка (8 ₽/ед.), сборка (12 ₽/операция), условно-постоянные (1200 ₽/день), удержания |
| Маркетплейс | комиссия продавца (12%), плата за доставку покупателя (129 ₽ mesh / 159 ₽ hub), логистическое удержание продавца (60 ₽), хранение продавца (перевод) | логистика, хранение в пользу ПВЗ, вознаграждение ПВЗ, бонус mesh, обратная логистика |
| Продавец | выручка от товара | закупка (70% цены), комиссия, логистическое удержание, хранение по фактическим дням, удержание за возврат |
| Покупатель | — | товар + доставка; срок в часах |

## 2. Логистика

```
mesh (в городе):  local_delivery_cost = 90 ₽, 3 ч
hub:              hub_handling 70 ₽ + trunk_per_order 10,5 ₽ + last_mile 55 ₽ = 135,5 ₽, 30 ч
trunk_per_order = 420 ₽ за рейс ÷ 40 отправлений
```

Магистраль считается на отправление, а не на рейс — иначе сравнение схем несопоставимо: в схеме mesh
рейс не нужен вообще, в схеме hub его стоимость распределяется на все отправления рейса.

Межгород в предложенной схеме — **предварительное размещение остатка**: магистраль оплачивается
консолидированно (10,5 ₽/заказ) и выполняется заранее, а в срок выдачи входит только локальный сегмент
(3 ч). Если остатка в городе получателя нет, схема недоступна и заказ идёт через хаб — это ограничение
показывается в API и UI, а не скрывается.

Маршрут в прототипе строится алгоритмом Дейкстры по графу активных сегментов. Схема выбирается по
минимальной стоимости при приемлемом сроке; если mesh дороже или медленнее, выбирается hub.

## 3. Правило про переводы

Плата за хранение, комиссия, вознаграждение ПВЗ — переводы внутри цепочки. Они меняют распределение
результата между участниками, но не создают нового результата. Поэтому:

```
результат цепочки = прибыль ПВЗ + прибыль маркетплейса + прибыль продавца
                  = оплата покупателя − закупка товара − внешние затраты логистики
                    − операционные затраты ПВЗ
```

В ledger сумма строк по заказу всегда равна `−внешние затраты логистики`. Это проверяется тестом
`test_transfers_do_not_create_chain_profit` и тестами API (`sum(ledger) == -90.0`).

## 4. Устойчивость и пороги

* **Низкая загрузка.** При фиксированных 1200 ₽/день ПВЗ выходит в ноль при 38 операциях в день
  при базовой доле дня ПВЗ 30% (`pvz_day_mesh_share_pct`); при доле локальных пар 62% — при 33 операциях/день;
  ниже — убыточен, выше — растёт маржа. В диапазоне 15–70% порог безубыточности — 41–32 операции в день (чувствительность в `ECON_REPORT.md`, 6.4).
  Пропускная способность в модели — 120 операций/день.
* **Длительное хранение.** Хранение — перевод: маркетплейс получает 7,5 ₽/день с продавца и передаёт
  ПВЗ, его маржа не меняется. Риск несёт продавец: при 52 днях плата за хранение съедает его прибыль.
  Продукт реагирует раньше — на 21 день или 600 ₽ начисленного хранения: уведомление ПВЗ и предложение
  перемещения за 60 ₽ (окупается за 8 дней хранения).
* **Возврат.** Удержание 60 ₽ с ПВЗ и 60 ₽ с продавца идут маркетплейсу, который платит обратную
  логистику 90 ₽; плечо возврата для маркетплейса — +30 ₽ к марже, а цепочка теряет 90 ₽ внешних затрат.
  Покупатель теряет стоимость доставки.
* **Очередь.** Ожидание покупателя считается по M/M/1 до 95% загрузки, дальше линейно. При 80% это
  0,8 ч, при 85% — 1,13 ч, при 95% — 3,8 ч: поэтому рабочая цель 80%, предупреждение 85%, а не «до 100%».
* **Срыв срока.** Просроченный заказ получает штраф 50 ₽ (с маркетплейса) и с вероятностью 35%
  отменяется: цепочка теряет маржу всех сторон и платит обратную логистику по пиковому коэффициенту
  ×1,25. Штраф сопоставляется с маржой маркетплейса (359 ₽), а не с ценой товара.
* **Ошибка/инцидент.** Отключение сегмента запускает перевыбор маршрута. Внутри города магистраль не
  используется по правилу модели: даже если хаб формально дешевле (135,5 ₽ против 180 ₽ через соседний
  ПВЗ), выбранной схемой остаётся mesh — магистраль не возит внутри города. Схема через хаб показывается
  в сравнении как альтернатива, а основание выбора выводится в UI.
* **Учёт в аналитике.** Сборка (12 ₽/заказ) и приёмка (8 ₽/ед.) относятся на ПВЗ-источник, где лежит
  остаток, а не на пункт выдачи; постоянные 1200 ₽/день вычитаются из прибыли за период. Без этого
  прибыль ПВЗ выглядела бы выше реальной, а один выданный заказ «окупал» бы день аренды.
* **Отмена до выдачи.** Отмена до отправки — это отсутствие операции, логистика не начисляется.
  Отмена просроченного заказа после начала доставки — обратная перевозка по коэффициенту ×1,25;
  именно этот сценарий моделирует `late_cancel_rate`.

## 5. Что не включено

* эквайринг, налоги, реальные платежи (шлюз — заглушка);
* аренда и ФОТ сверх условно-постоянной ставки, амортизация, маркетинг;
* страхование, потери и недостачи сверх удержаний модели;
* расписание магистральных рейсов (стоимость консолидирована);
* клиентское приложение покупателя и его аналитика;
* юридические обязательства и реальные SLA.

**Справочные параметры, в расчётах не участвуют.** `return_rate_pct`, `incident_rate_pct`,
`accurate_stock_bonus_rub` и `pvz.capacity_cells_default` остаются в `params.yaml` и схеме валидации как
ориентиры для этапа пилота: модель считает возврат по `return_reverse_fee_rub` и обратной логистике,
инцидент — по перепробегу маршрута, а бонус за точность и объём склада — по ячейко-дням и
`ops_per_day_capacity`. Менять или удалять их нельзя, пока продуктовые сценарии не перейдут на эти ставки.

## 6. Как пересчитать

```bash
python economics/report.py          # обновит docs/ECON_REPORT.md
python -m pytest economics/tests -q  # проверит числа и разделы отчёта
```

Любое изменение `params.yaml` автоматически отражается и в API (пересчёт при старте), и в отчёте —
единый источник чисел исключает расхождение презентации и кода.
