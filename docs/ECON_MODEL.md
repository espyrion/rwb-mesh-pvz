# Экономическая модель

Документ описывает, что и как считается в прототипе, какие допущения приняты и где границы модели.
Числовые расчёты — в [ECON_REPORT.md](ECON_REPORT.md) (генерируется из модели, не правится руками).
Источник параметров — `economics/params.yaml`.

> **Дисклеймер.** Тарифы, бонусы, штрафы, лимиты ответственности и SLA — элементы предложенной командой
> модели. Они не являются действующими тарифами RWB или его партнёров. Данные синтетические.

## 1. Четыре стороны

Каждый заказ описывается с точки зрения четырёх участников:

| Сторона | Доходы | Затраты |
|---|---|---|
| ПВЗ | плата за выдачу (25 ₽), хранение (5 ₽/ячейка·день), бонус за заказ без хаба (15 ₽), плата за перемещение | приёмка (8 ₽/ед.), сборка (12 ₽/операция), условно-постоянные (1200 ₽/день), удержания |
| Маркетплейс | комиссия продавца (12%), плата за доставку покупателя (119 ₽ mesh / 159 ₽ hub) | логистика, хранение, вознаграждение ПВЗ, бонус mesh |
| Продавец | выручка от товара | комиссия маркетплейса |
| Покупатель | — | товар + доставка; срок в часах |

## 2. Логистика

```
mesh (в городе):  local_delivery_cost = 90 ₽, 3 ч
hub:              hub_handling 70 ₽ + trunk_per_order 10,5 ₽ + last_mile 55 ₽ = 135,5 ₽, 30 ч
trunk_per_order = 420 ₽ за рейс ÷ 40 отправлений
```

Магистраль считается на отправление, а не на рейс — иначе сравнение схем несопоставимо: в схеме mesh
рейс не нужен вообще, в схеме hub его стоимость распределяется на все отправления рейса.

Маршрут в прототипе строится алгоритмом Дейкстры по графу активных сегментов. Схема выбирается по
минимальной стоимости при приемлемом сроке; если mesh дороже или медленнее, выбирается hub. Для
межгорода mesh недоступен (нет локального пути), поэтому заказ идёт через хаб.

## 3. Правило про переводы

Плата за хранение, комиссия, вознаграждение ПВЗ — переводы внутри цепочки. Они меняют распределение
результата между участниками, но не создают нового результата. Поэтому:

```
результат цепочки = прибыль ПВЗ + прибыль маркетплейса + прибыль продавца
                  = оплата покупателя − внешние затраты логистики − операционные затраты ПВЗ
```

В ledger сумма строк по заказу всегда равна `−внешние затраты логистики`. Это проверяется тестом
`test_transfers_do_not_create_chain_profit` и тестами API (`sum(ledger) == -90.0`).

## 4. Устойчивость и пороги

* **Низкая загрузка.** При фиксированных 1200 ₽/день ПВЗ выходит в ноль при ~38 операциях в день;
  ниже — убыточен, выше — растёт маржа. Пропускная способность в модели — 120 операций/день.
* **Длительное хранение.** Доход маркетплейса падает на 7,5 ₽/день (1,5 ячейки × 5 ₽); при ~38 днях
  заказ становится убыточным. Продукт реагирует раньше — на 21 день или 600 ₽ начисленного хранения:
  уведомление ПВЗ и предложение перемещения за 60 ₽.
* **Возврат.** Удержание 60 ₽ покрывает обратную логистику (90 ₽) лишь частично — разницу берёт
  маркетплейс; это осознанное решение, чтобы не делать возврат дорогим для ПВЗ. Покупатель теряет
  стоимость доставки.
* **Ошибка/инцидент.** Отключение сегмента запускает перевыбор маршрута. Внутри города магистраль не
  используется по правилу модели: даже если хаб формально дешевле (135,5 ₽ против 180 ₽ через соседний
  ПВЗ), выбранной схемой остаётся mesh — магистраль не возит внутри города. Схема через хаб показывается
  в сравнении как альтернатива, а основание выбора выводится в UI.
* **Учёт в аналитике.** Сборка (12 ₽/заказ) и приёмка (8 ₽/ед.) относятся на ПВЗ-источник, где лежит
  остаток, а не на пункт выдачи; постоянные 1200 ₽/день вычитаются из прибыли за период. Без этого
  прибыль ПВЗ выглядела бы выше реальной, а один выданный заказ «окупал» бы день аренды.

## 5. Что не включено

* эквайринг, налоги, реальные платежи (шлюз — заглушка);
* аренда и ФОТ сверх условно-постоянной ставки, амортизация, маркетинг;
* страхование, потери и недостачи сверх удержаний модели;
* расписание магистральных рейсов (стоимость консолидирована);
* клиентское приложение покупателя и его аналитика;
* юридические обязательства и реальные SLA.

## 6. Как пересчитать

```bash
python economics/report.py          # обновит docs/ECON_REPORT.md
python -m pytest economics/tests -q  # проверит числа и разделы отчёта
```

Любое изменение `params.yaml` автоматически отражается и в API (пересчёт при старте), и в отчёте —
единый источник чисел исключает расхождение презентации и кода.
