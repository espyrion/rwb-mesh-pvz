# План тиражирования и техплан

Документ отвечает на два вопроса: как вывести решение из прототипа в пилот и что нужно технически,
чтобы пилот выдержал нагрузку. Отдельно указано, что уже реализовано, а что планируется, — без
смешивания.

## 1. Пилот: рамки и условия

| Параметр | Значение пилота |
|---|---|
| Города | 2 (Йошкар-Ола, Казань) |
| ПВЗ | 8–16 точек, от 50 ячеек, загрузка не выше 70% на старте |
| Продавцы | 30–50, с остатком не менее 20 SKU в городе пилота |
| Длительность | 12 недель (2 недели подготовки + 10 недель операций) |
| Объём | до 2 000 заказов в неделю, из них mesh — целево ≥40% |
| Деньги | только программные расчёты; платёжный шлюз не подключается |

Критерий старта: подписаны соглашения с ПВЗ, проведено обучение, в системе заведены остатки и тарифы,
пройдены пять демо-сценариев на тестовом контуре.

## 2. Этапы и ворота (go / no-go)

| Этап | Длительность | Что делаем | Ворота перехода |
|---|---|---|---|
| 0. Подготовка | 2 недели | договоры, тарифы, обучение, заведение ПВЗ и продавцов, нагрузочный тест | 100% ПВЗ прошли тестовые 20 заказов, точность остатков ≥95% |
| 1. Пилот в одном городе | 4 недели | 4–6 ПВЗ, 10–15 продавцов, ежедневный разбор инцидентов | доля mesh ≥30%, возвраты ≤5%, утилизация 40–70% |
| 2. Расширение города | 3 недели | +4–6 ПВЗ, +15 продавцов, включение длительного хранения и перемещений | доля mesh ≥40%, срок выдачи ≤4 ч, удержание >21 дня ≤3% |
| 3. Второй город | 3 недели | межгород через хаб, сравнение с базовой схемой | unit-экономика маркетплейса ≥0 на заказ, SLA выполнен |
| 4. Масштабирование | далее | регионы, автоматизация пополнения, интеграции | решение по итогам 1–3 |

Решение «no-go» принимается, если после 4 недель пилота доля mesh ниже 25%, утилизация ПВЗ ниже 30%
или убыток маркетплейса на заказ превышает 50 ₽. Тогда схема пересобирается (тарифы/сеть), а не
масштабируется.

## 3. Подключение ПВЗ

1. **Отбор.** Ёмкость ≥50 ячеек, свободная загрузка, город с плотностью продавцов, готовность к
   двум операциям в день (приёмка/выдача).
2. **Договор.** Тарифы модели (выдача 25 ₽, хранение 5 ₽/ячейка·день, бонус 15 ₽ за mesh, удержание 60 ₽
   за возврат), лимит ответственности, SLA, порядок перемещений.
3. **Обучение (2 часа).** Роли, приёмка, сборка, выдача, возврат, инциденты, работа с остатками.
4. **Симулятор.** 20 тестовых заказов на тестовом контуре, включая возврат и длительное хранение.
5. **Приёмка.** Точность остатков ≥95%, время операции ≤3 минут, отсутствие блокирующих ошибок.

## 4. Подключение продавцов

Критерии: остаток в городе пилота, регулярные поставки, готовность маркировать SKU. Обучение — 1 час:
как оформить заказ, как читать аналитику и статусы. Интеграция — API или выгрузка остатков; на пилоте
допускается ручное заведение.

## 5. Метрики пилота

| Метрика | Целевое значение | Как считаем |
|---|---|---|
| Доля заказов mesh | ≥40% | заказы с `route.kind=mesh` / все выданные |
| Срок выдачи | ≤4 ч в городе, ≤30 ч межгород | `issued_at − created_at` |
| Точность остатков | ≥98% | расхождение инвентаризации с системой |
| Утилизация ПВЗ | 50–75% | `used_cells / capacity_cells` |
| Длительное хранение | ≤2% заказов | заказы с начислением >600 ₽ или >21 дня |
| Возвраты | ≤3% | `returned / issued` |
| Инциденты на 100 заказов | ≤5 | `incident` за период |
| Прибыль ПВЗ | ≥0 при загрузке ≥38 операций/день | аналитика ПВЗ |
| Прибыль маркетплейса на заказ | ≥0 | ledger по стороне |

## 6. Риски и меры

| Риск | Влияние | Мера |
|---|---|---|
| Каннибализация существующей выдачи | падение оборота классических ПВЗ | сравнивать потоки по точке, не дублировать тарифы, вводить mesh-бонус только на новые заказы |
| Нехватка ёмкости | отказы в приёмке | порог 85%, прогноз загрузки, перемещение остатка |
| Ошибки остатков | отмены заказов | обязательная приёмка по SKU, сверка, бонус за точность |
| Сезонность | пики и простои | резерв 20% ёмкости, гибкие тарифы хранения |
| Зависимость от трафика продавцов | низкая загрузка ПВЗ | порог 38 операций/день, субсидия только на старте |
| Юридические ограничения | нельзя запустить | тарифы — предложение, не оферта; проверка до пилота |
| Утечка данных | репутация | разграничение ролей, аудит, шифрование, доступ по OIDC |

## 7. Техплан

### Архитектура

```
Браузер (ПВЗ / продавец)
        │ HTTPS
        ▼
   nginx (web) ──► FastAPI (api) ──► SQLite (MVP)
                        │
                        ├─ routing (Дейкстра по графу сегментов)
                        ├─ ledger (денежные начисления, идемпотентность)
                        ├─ storage (ёмкость, тарифы, длительное хранение)
                        └─ notifications (лента событий)
```

Планируемое для пилота: PostgreSQL, очередь задач (напоминания, пересчёты), платёжный шлюз-заглушка с
идемпотентными операциями, сервис аутентификации.

### Нагрузка

Расчёт: 16 ПВЗ × 120 операций/день = 1 920 операций/день, пик 5 запросов/с, среднее время ответа
<150 мс на SQLite при индексах по `order.status`, `ledger.order_id`, `item.stored_pvz_id`. Переход на
PostgreSQL — при >50 запросов/с или >1 млн строк ledger. Горизонтальное масштабирование API —
stateless-процессы за nginx, БД с репликой.

### Доступ и роли

На MVP аутентификации нет (UI разделён по ролям визуально). В пилоте: OIDC, роли `pvz`, `seller`,
`operator`, `admin`; ПВЗ видит только свои остатки и начисления, продавец — только свои товары и заказы.
Все операции пишутся в audit-log.

### Журналирование и наблюдаемость

* структурные логи JSON: `ts`, `request_id`, `method`, `path`, `status`, `duration_ms`, `party`;
* audit-log действий: приёмка, выдача, возврат, перемещение, отключение сегмента;
* healthcheck `/health`, метрики (планируется Prometheus): RPS, p95, ошибки 4xx/5xx, число открытых
  инцидентов, загрузка ПВЗ.

### Повторные запросы и целостность

* `POST /orders` идемпотентен по `idempotency_key`;
* `assemble`/`issue`/`return` идемпотентны по статусу (`idempotent_replay`);
* ledger — единственный источник денежных расчётов, сумма по заказу = −внешняя логистика;
* транзакции на операцию, `PRAGMA foreign_keys=ON`.

### Backup / restore

* SQLite: ежедневный `VACUUM INTO` + копия в объектное хранилище, retention 14 дней;
* проверка восстановления — ежемесячно на тестовом контуре (цель: RPO ≤24 ч, RTO ≤2 ч);
* в пилоте PostgreSQL: WAL-архив, PITR, ежедневный логический дамп; restore-drill раз в месяц.

### Доступность

SLO 99,5% в часы работы ПВЗ. Два экземпляра API за nginx, healthcheck каждые 30 с, автоматический
перезапуск контейнера. Деплой — blue-green, миграции — отдельным шагом с проверкой отката.

### Что реализовано, а что планируется

| Блок | Реализовано в MVP | Планируется |
|---|---|---|
| Приёмка, заказы, выдача, возврат | да | — |
| Маршруты mesh/hub, инциденты, перевыбор | да | прогноз загрузки, резервирование маршрута |
| Экономика, ledger, аналитика | да (программные расчёты) | платёжный шлюз, сверка с биллингом |
| Виртуальные часы, длительное хранение | да | фоновые задачи по расписанию |
| UI ПВЗ и продавца | да (одно приложение с ролями) | клиент покупателя, мобильная версия |
| Аутентификация и роли | нет | OIDC, разграничение доступа |
| Масштабирование | SQLite, один процесс | PostgreSQL, очередь, реплики |
| Мониторинг | healthcheck | Prometheus, алерты, трассировка |
| Backup | инструкция и скрипт дампа | PITR, регулярные учения |
