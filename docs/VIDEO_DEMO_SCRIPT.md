# Сценарий видео: демо-кокпит и «зелёная зона»

> Хронометраж — 3–4 минуты. Все числа на экране приходят из API (`economics/params.yaml` →
> `/api/v1/economics/scenario` и другие эндпоинты). В кадре не называйте числа «прогнозом RWB»:
> это детерминированная модель. Если значение на экране отличается от этого текста — верьте экрану,
> текст описывает только порядок действий.

## Подготовка стенда (до записи)

```bash
# отдельная БД и API на 8001, живой стенд :8000 не трогаем
cd api && DATABASE_URL=sqlite:////tmp/mesh-demo.db PYTHONPATH=.. \
  ../.venv/bin/python -m uvicorn app.main:app --port 8001

# статика + прокси /api/v1 → 8001
python3 /tmp/proxy8001.py       # отдаёт web/src на :8010

# проверка, что стенд пригоден для записи
API_URL=http://localhost:8001 MESH_API_KEY=demo-admin-key .venv/bin/python scripts/demo.py
```

Требования к кадру: светлая тема не нужна, шрифт браузера — 100%, окно 1440×900.
Роль API в левом нижнем углу: **Маркетплейс** (для скоринга и отказа узла), переключение на
**ПВЗ** показываем только в кабинете ПВЗ, если хотите подчеркнуть права.

## Кадр 1. Дашборд (0:00–0:15)

Показать: карточки заказов и логистики, таблицу загрузки ПВЗ.

Реплика: «Заказы, деньги и загрузка точек — один экран. Порог предупреждения по загрузке
подписан здесь же и берётся из модели, а не из вёрстки».

## Кадр 2. Экономика: зелёная зона четырёх сторон (0:15–0:50)

1. Открыть **Экономика**. Первый блок — «Зелёная зона 4 сторон».
2. Показать бейдж «зелёная зона: ДА/НЕТ» и объяснить: он считается из ответа API
   (`order.compare`), а не задан в коде.
3. Пройти по чек-листу: ΔПВЗ (строго > 0), Δмаркетплейса (≥ 0), Δпродавца (≥ 0),
   Δпокупателя — цена и срок одновременно (< 0). У каждой строки видно факт, порог и статус.
4. Показать две карточки «границы приемлемости покупателя»: лимит роста цены и лимит роста срока
   из `buyer_acceptance`, рядом — фактическое изменение и вердикт «в допуске / вне допуска».
5. Прокрутить таблицу «Четыре стороны: через хаб против mesh»: прибыль ПВЗ, маркетплейса,
   продавца, цепочки, платёж покупателя и срок — с Δ и Δ%.

Реплика: «Зелёная зона — это не лозунг. Четыре условия проверяются по числам, и если хотя бы одно
не выполняется, бейдж становится красным. Покупатель не должен платить больше и ждать дольше —
это два отдельных условия, оба обязательны».

## Кадр 3. «Что если»: ползунки (0:50–1:20)

1. Дёрнуть **бонус ПВЗ за заказ без хаба** — блок «зелёная зона» и «День ПВЗ» пересчитываются.
2. Дёрнуть **долю заказов без хаба** — меняются ΔПВЗ и точка безубыточности.
3. Дёрнуть **срок хранения** — меняется стоимость хранения и запас маркетплейса.
4. Дёрнуть **операции ПВЗ в день** — меняется прибыль дня и загрузка мощности.
5. Обратить внимание на индикатор «пересчитываю сценарий…»: запрос идёт с задержкой 350 мс,
   устаревшие ответы отменяются, поэтому цифры не «прыгают» между состояниями.

Реплика: «Четыре ручки — четыре реальных параметра расчёта: бонус mesh, доля mesh, срок хранения
и число операций. Остальные ставки модели в интерфейсе показаны только для чтения: API принимает их
query-параметрами, но в этой ветке вынесены именно четыре ручки, чтобы в кадре не путаться.

## Кадр 4. Кабинет ПВЗ: скоринг и сверка (1:20–1:50)

1. Открыть **Кабинет ПВЗ**, выбрать точку.
2. В карточке точки показать «Точность аудита», «SLA-рейтинг», «Последняя сверка»
   (`audit_accuracy_pct`, `audit_sla_rating`, `last_audit_at`).
3. Блок **Скоринг размещения**: ввести SKU, количество, ячеек на штуку, оставить спрос и
   оборачиваемость пустыми (их оценит API) → «Оценить». Показать score и порог, рекомендацию,
   уверенность, таблицу компонентов с весами и баллами и список причин.
4. Блок **Сверка остатков**: изменить фактическое количество в одной строке, отправить.
   Показать расхождения по строкам, удержания, точность до/после и SLA-рейтинг.
   Нажать «Отправить сверку» ещё раз с тем же фактом — в ответе `idempotent`, новых удержаний нет.

Реплика: «Скоринг отвечает на вопрос «ставить партию в город или гнать через хаб», сверка —
на вопрос «сколько мы реально потеряли». Обе цифры считает сервер, интерфейс их только показывает».

## Кадр 5. Демо-кокпит: пять сценариев (1:50–3:20)

Открыть **Демо-кокпит**. Нажать «Прогнать все 5 шагов» (или идти по шагам, комментируя).

| Шаг | Что нажать | Что сказать | Что должно быть на экране |
|---|---|---|---|
| 1. Спокойный день | «Выполнить шаг» | «Внутригородская пара, обе точки ниже порога — маршрут идёт по mesh» | PASS, `chosen=mesh`, `overflow=false`, стоимость и срок mesh против хаба |
| 2. Пиковая нагрузка | «Выполнить шаг» | «Принимаем партию на точку-приёмник: загрузка переходит порог, маршрут уходит на хаб» | PASS, «загрузка X% → Y% (порог Z%)», триггер overflow по стороне `to` |
| 3. Отказ узла | «Выполнить шаг» | «Выводим точку из строя: остатки эвакуируются, заказы переадресуются, открыт инцидент» | PASS, число партий и ячеек эвакуации, стоимость перемещений, инцидент |
| 4. Восстановление | «Выполнить шаг» | «Возвращаем точку в строй — маршрут считается снова» | PASS, занято/свободно ячеек, маршрут и стоимость |
| 5. Переключение на хаб | «Выполнить шаг» | «Межгород: локального маршрута нет, работают хаб и магистраль» | PASS, плечи `trunk`, стоимость, срок, платёж покупателя |

После шагов показать:
* бейдж **«итог: 5/5»** в шапке кокпита;
* «Лог различий» — по строке на каждое изменение: маршрут, загрузка, опоздания, деньги;
* что FAIL не прячется: если условие не выполнено, шаг краснеет и печатает причину
  (например, «точка выведена из строя — шаг 2 невозможен»).

Реплика: «Кокпит ничего не изображает: каждый шаг — реальные запросы к API, PASS/FAIL считается
по полям ответа. Поэтому его можно показывать на любой базе: он сам решает, нужна ли новая партия,
и печатает то, что вернул сервер».

Кнопка **«Сбросить кокпит»** очищает только экран (не данные стенда). Повторный прогон
на той же базе работает: перед стартом кокпит выдаёт демо-партии прошлых прогонов через обычный
заказ (строка «выданы демо-партии…» в шапке), пиковую нагрузку создаёт переносом остатков внутри
города, а не приёмкой новых, SKU подбираются уникальные.

## Кадр 6. Тот же прогон из терминала (3:20–3:40)

```bash
API_URL=http://localhost:8001 MESH_API_KEY=demo-admin-key .venv/bin/python scripts/demo.py
```

Показать строки `PASS` по шагам и финальное `итог: 5/5`. Это резерв, если браузер подвиснет
во время записи: скрипт проходит те же пять сценариев против того же API.

## Если что-то пошло не так

| Симптом | Причина | Что делать |
|---|---|---|
| Шаг 1 FAIL, «overflow=true» | на стенде все точки уже загружены | пересоздать БД `/tmp/mesh-demo.db` и перезапустить API на 8001 |
| Шаг 3 PASS с пометкой «уже была выведена» | точка была выключена до записи | это корректное поведение, шаг 4 вернёт её в строй |
| Скоринг вернул 403 | роль API — «ПВЗ» | переключить роль на «Маркетплейс» |
| «нет данных» вместо числа | API не отдал поле или запрос упал | не подставлять ноль: показать ошибку в кадре и пересчитать |

## Чего не говорить

* «Мы заменим логистику RWB» — в модели только расчёт, перевозок нет.
* «Экономия покупателя N рублей» без оговорки «в допущениях модели».
* «Зелёная зона всегда» — она зависит от параметров; ползунки это показывают.
