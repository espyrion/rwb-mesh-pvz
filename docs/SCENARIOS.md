# Демонстрационные сценарии

Пять обязательных сценариев ТЗ. Каждый воспроизводится в UI и автотестом
(`api/tests/test_scenarios.py`, запуск с `-s` печатает отчёт). Сквозной прогон против живого API —
`scripts/demo.py`.

## Сценарий 1. Городской заказ без хаба

**Что делаем.** Продавец оформляет заказ товара, который уже лежит на ПВЗ YOL-01, с выдачей на YOL-03.

**Ожидаемо.** Маршрут mesh, 90 ₽, 3 ч. Покупатель платит 19 019 ₽ (товар 18 900 + доставка 119).
После выдачи: ПВЗ +40 ₽ (25 выдача + 15 бонус), продавец +16 632 ₽ (товар минус 12%), маркетплейс
+2 257 ₽, покупатель −19 019 ₽. Сумма начислений = −90 ₽ (внешняя логистика).

**Что проверяет.** Приёмка/резерв/сборка/выдача, маршрутизация mesh, денежная сходимость, отсутствие
хаба в цепочке.

## Сценарий 2. Межгородской заказ через хаб

**Что делаем.** Заказ с YOL-01 (Йошкар-Ола) на KZN-01 (Казань).

**Ожидаемо.** mesh недоступен (нет локального пути между городами), выбирается hub: обработка 70 ₽ +
магистраль 10,5 ₽ + последняя миля 55 ₽ = 135,5 ₽, 30 ч. Покупатель платит 19 059 ₽. Заказ проходит
статусы routed → assembled → in_transit → issued; ПВЗ получает 25 ₽ без mesh-бонуса. Выдать заказ сразу
после сборки нельзя: `POST /orders/{id}/issue` вернёт 409, пока не выполнен транзит.

**Что проверяет.** Выбор базовой схемы при отсутствии локального маршрута, сегменты и время,
корректность начислений при межгороде.

## Сценарий 3. Возврат после выдачи

**Что делаем.** Выдаём заказ, затем оформляем возврат в течение 7 дней.

**Ожидаемо.** Обратный маршрут (mesh, 90 ₽), остаток возвращается на исходный ПВЗ (ячейки занимаются
снова), продавцу — сторно выручки, ПВЗ — удержание 60 ₽, маркетплейс оплачивает обратную логистику.
Сумма ledger по заказу = −180 ₽ (90 туда + 90 обратно). Покупатель теряет стоимость доставки.
При сборке партия разделяется: в заказ уходит проданное количество, остальное остаётся на ПВЗ-источнике,
поэтому возврат возвращает ровно количество заказа, а не всю исходную партию.

**Что проверяет.** Обратный маршрут, восстановление остатков и ячеек, сторно и удержание, срок возврата
(после 7 дней — 409).

## Сценарий 4. Логистическая ошибка со сменой маршрута

**Что делаем.** На активном заказе отключаем сегмент, по которому он едет (YOL-01 → YOL-03).

**Ожидаемо.** Открывается инцидент, система пересчитывает маршрут: прямой сегмент недоступен, ближайшая
альтернатива — локальный путь через соседний ПВЗ (180 ₽, два сегмента). Магистраль внутри
города не используется по правилу модели, поэтому выбирается mesh через соседнюю точку; заказ получает
статус `rerouted`, инцидент — `resolved` со ссылкой на новый маршрут. Схема через хаб показывается в
сравнении как альтернатива (135,5 ₽), но не может быть выбрана для внутригородского заказа. Если путь не
найден (отключена единственная связь до пункта), инцидент остаётся открытым, `POST /incidents/{id}/reroute`
возвращает 409 до восстановления сегмента.

**Что проверяет.** Обработку нештатной ситуации, прозрачность основания выбора, восстановление после
включения сегмента.

## Сценарий 5. Длительное хранение и перемещение остатка

**Что делаем.** Сдвигаем виртуальное время на 25 дней.

**Ожидаемо.** Начисляется хранение (5 ₽ × ячейки × фактически прошедшие дни; при первом сдвиге дней
учитывается только время с момента приёмки), ПВЗ получает уведомление о длительном
хранении с предложением переместить остаток в менее загруженный ПВЗ того же города за 60 ₽. После
перемещения ячейки освобождаются на исходной точке и занимаются на новой, затраты относятся на
маркетплейс, остаток снова становится «свежим» для порога.

**Что проверяет.** Пересчёт хранения по виртуальным часам, пороги 21 день / 600 ₽, уведомления,
перемещение и его стоимость.

## Сценарий 6. Отмена заказа и отслеживание покупателем

**Что делаем.** Оформляем городской заказ, копируем у него ссылку покупателю (кнопка «Ссылка покупателю» —
в ссылке случайный токен), открываем раздел «Покупатель», затем
отменяем до выдачи (`POST /orders/{id}/cancel`) и обновляем страницу отслеживания.

**Ожидаемо.** Покупатель видит «Маршрут построен» и историю событий; после отмены — «Отменён».
Резерв снимается, остаток возвращается в ячейки ПВЗ-источника (если заказ уже был собран — ячейки
переезжают обратно), логистика не начисляется. Отмена после выдачи или транзита запрещена (409).

**Что проверяет.** Публичная карточка без комиссий и расчётов продавца, идемпотентность отмены,
возврат ячеек, границы статусной модели.

## Как показывать

1. `docker compose up --build`.
2. Дашборд — общая картина и сходимость ledger.
   Карта сети — схема городов и магистрали, наведение на сегменты, подсветка маршрута заказа; там же
   кнопка «Вывести из строя» показывает эвакуацию остатков и переадресацию заказов.
3. Кабинет продавца — оформить городской и межгородской заказ (сценарии 1–2).
4. Заказы — собрать, выдать, показать «Начисления» (сценарий 1), вернуть (сценарий 3).
5. Маршруты и сеть — сравнить схемы, отключить сегмент (сценарий 4), показать инцидент.
6. Время и уведомления — сдвинуть на 25 дней, выполнить перемещение в кабинете ПВЗ (сценарий 5).
7. Покупатель — ввести код заказа, показать историю; вернуться в «Заказы» и отменить заказ (сценарий 6).

Если UI недоступен — `python3 scripts/demo.py` прогоняет те же шесть сценариев через API и печатает
таблицы (годится для backup-видео).
