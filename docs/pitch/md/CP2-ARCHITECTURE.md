# Mesh-ПВЗ: как система устроена изнутри и снаружи

> Для защиты ЧП2 («Техническая сторона MVP») и ответов на вопросы жюри.
> Все пути — относительно корня репозитория `~/mesh-pvz`.

---

## 1. Снаружи: что видит пользователь

### 1.1 Три роли — один интерфейс

Web-приложение на `:5173` (nginx раздаёт `web/src/`). Роли переключаются в боковом меню, авторизация — заголовок `X-API-Key`. Никакой регистрации, сессий, кук: ключи жёстко заданы в `api/app/auth.py`.

| Роль | Ключ | Что видит |
|------|------|-----------|
| ПВЗ | `demo-pvz-key` | Приёмка товара, остатки, заказы на сборку/выдачу, сверка остатков, скоринг размещения, уведомления (включая алерт 21 день) |
| Продавец | `demo-seller-key` | Остатки на точках, оформление заказа, аналитика (выручка, комиссия, прибыль) |
| Админ | `demo-admin-key` | Все эндпоинты без ограничений |

### 1.2 Основные экраны UI

| Вкладка | Что делает |
|---------|------------|
| Дашборд | Сводка: загрузка ПВЗ, 4 стороны, последние заказы |
| Карта сети | Визуализация графа ПВЗ (Leaflet), статус точек и рёбер |
| Экономика | Ползунки «Что если» (4 параметра → API → пересчёт), «Зелёная зона 4 сторон», «День ПВЗ», «Чувствительность» |
| Кабинет ПВЗ | Приёмка, остатки, сборка/выдача, скоринг размещения, сверка, уведомления |
| Кабинет продавца | Остатки, оформить заказ, заказы, аналитика |
| Заказы | Все заказы с фильтрацией по статусу |
| Демо-кокпит | 7 сценариев одним кликом |
| Время и уведомления | Виртуальные часы, список уведомлений |

### 1.3 Путь продавца (сквозной сценарий)

1. **Скоринг размещения** (Кабинет ПВЗ → «Скоринг размещения»): продавец вводит SKU, количество, ячейки, спрос → `POST /catalog/placement-score` → score 0–100 и рекомендация `mesh_pvz` или `hub`.
2. **Приёмка товара** (Кабинет ПВЗ → «Приёмка»): товар физически поступает на точку, создаётся партия в БД.
3. **Заказ** (Кабинет продавца → «Оформить заказ»): продавец выбирает свой товар и ПВЗ получателя → `POST /orders` → автоматический выбор маршрута mesh/hub.
4. **Алерт 21 день** (Кабинет ПВЗ → «Уведомления»): если партия лежит >21 дня, виртуальные часы генерируют уведомление `long_storage` с предложением переместить остаток в менее загруженный ПВЗ за 60 ₽.

## 2. Изнутри: архитектура кода

### 2.1 Слои

```
web/src/          — vanilla JS (без фреймворков, без сборки)
    app.js        — единое приложение: роутинг, рендеринг, API-запросы
    map.js        — карта сети (Leaflet)
    index.html    — точка входа

api/              — FastAPI + SQLAlchemy
    app/
        main.py           — сборка приложения, lifespan (инициализация БД)
        models.py         — ORM-модели (Pvz, Item, Order, Ledger, Incident, Notification, Clock…)
        schemas.py        — Pydantic-схемы (запросы/ответы)
        db.py             — подключение SQLite (WAL-режим)
        auth.py           — проверка X-API-Key и ролей
        clock.py          — виртуальные часы (можно перематывать вперёд)
        routers/
            catalog.py        — ПВЗ, товары, приёмка, скоринг, аудит, продавцы
            orders.py         — заказы: создание, сборка, транзит, выдача, отмена
            returns.py        — возвраты с refund-проводками
            routes_api.py     — рёбра графа, сравнение маршрутов mesh/hub
            analytics.py      — аналитика ПВЗ, продавца, сводка
            economics.py      — сценарий «что если», экономический отчёт
            incidents.py      — инциденты и переадресация
            notifications.py  — уведомления (long_storage и др.)
            clock_api.py      — управление виртуальными часами
            track.py          — карточка покупателя по токену
    tests/          — 143 теста (pytest + httpx TestClient)

economics/        — чистая Python-модель (не зависит от FastAPI)
    __init__.py       — загрузка params.yaml
    model.py          — формулы: route_cost, storage_cost, pvz_pnl, marketplace_pnl, seller_pnl, buyer_cost, order_economics, compare
    scenario.py       — сценарий «что если»: пересчёт при изменённых ставках, безубыточность, чувствительность
    network.py        — симуляция дня сети (M/M/1, overflow, seed 42)
    report.py         — генератор ECON_REPORT.md
    tests/            — 28 тестов (модель, регрессии, отчёт)
```

### 2.2 Ключевые проектные решения

**Единый источник чисел.** Все тарифы, ставки и пороги — в `economics/params.yaml`. API читает его при старте (`economics/__init__.py::params()`). UI не содержит ни одной цифры — всё приходит из ответов API. `ECON_REPORT.md` генерируется из модели и сверяется тестом.

**Виртуальные часы.** Вместо реального времени — таблица `clock` с одним полем `virtual_now`. Можно перемотать вперёд через `POST /clock/advance`. Это позволяет показать сценарий «длительное хранение >21 дня» за секунду, не ожидая реальных трёх недель.

**Маршрутизация mesh/hub.** Для каждого заказа `POST /orders` автоматически вычисляет два маршрута (mesh и hub) и выбирает оптимальный по правилам:
- Если ПВЗ отправителя и получателя в одном городе — mesh (локальная доставка 90 ₽).
- Если в разных — межгород: предразмещённый остаток (mesh, магистраль оплачена заранее) либо хаб (135,50 ₽).
- При загрузке ПВЗ >85% (`overflow_utilization_threshold`) — принудительный хаб.

**Эвакуация при отказе узла.** `POST /pvz/{id}/disable` запускает эвакуацию: остатки распределяются по соседним точкам с учётом свободной ёмкости и расстояния, заказы переадресуются. Восстановление — `POST /pvz/{id}/enable`.

**Ledger (двойная запись).** Каждая операция пишет проводки в таблицу `ledger` (party, kind, amount_rub). Сумма всех проводок всегда ноль — это проверяется тестом `test_chain_identity_holds`. Четыре стороны: `pvz`, `marketplace`, `seller`, `buyer`.

**Сходимость с хабом.** Функция `compare()` в `economics/model.py` считает разницу mesh − hub для каждой стороны. «Зелёная зона» в UI — это когда все четыре условия выполнены одновременно: ПВЗ в плюсе, МП не в минусе, продавец не в минусе, покупатель платит меньше и получает быстрее.

### 2.3 База данных

SQLite в WAL-режиме, один файл `meshdata/mesh.db` (volume в Docker). Основные таблицы:

| Таблица | Назначение |
|---------|------------|
| `pvz` | Точки выдачи: город, ёмкость, координаты, статус, точность остатков |
| `items` | Партии товара: SKU, продавец, ПВЗ, количество, резерв, ячейки |
| `orders` | Заказы: статус, маршрут, стоимости, флаги mesh/overflow |
| `ledger` | Проводки: сторона, вид, сумма, привязка к заказу |
| `incidents` | Инциденты: отказ узла, переадресация |
| `notifications` | Уведомления: long_storage, аудит |
| `edges` | Рёбра графа между ПВЗ |
| `clock` | Виртуальное время (одна строка) |
| `sellers` | Продавцы |

### 2.4 Docker-стенд

Два контейнера в `docker-compose.yml`:
- **api** — Python 3.14, uvicorn на `:8000`, volume `meshdata` для БД
- **web** — nginx:alpine на `:5173`, раздаёт `web/src/`, проксирует `/api/` на api

Сборка: `docker compose up -d --build`. Полный сброс: `docker compose down -v`.

## 3. Числа и их происхождение

### 3.1 Откуда берутся цифры на экране

```
economics/params.yaml          — единственный источник тарифов
        ↓
economics/__init__.py::params() — загрузка при старте API
        ↓
api/app/routers/economics.py   — GET /economics/scenario (пересчёт «что если»)
api/app/routers/orders.py      — POST /orders (расчёт маршрута и стоимости)
api/app/routers/analytics.py   — GET /analytics/* (сводка по ledger)
        ↓
web/src/app.js                 — рендеринг, ни одной своей цифры
```

### 3.2 Ключевые числа (эталон: товар 2 500 ₽, 1,5 ячейки, 3 дня)

| Показатель | Хаб | Mesh | Δ |
|------------|-----|------|---|
| Логистика | 135,50 ₽ / 30 ч | 90,00 ₽ / 3 ч | −45,50 ₽ / −27 ч |
| ПВЗ (прибыль) | 27,50 ₽ | 39,50 ₽ | +12,00 ₽ |
| Маркетплейс (прибыль) | 358,50 ₽ | 382,00 ₽ | +23,50 ₽ |
| Продавец (прибыль) | 367,50 ₽ | 367,50 ₽ | 0 ₽ |
| Покупатель (платит) | 2 659,00 ₽ | 2 649,00 ₽ | −10,00 ₽ |
| Цепочка (прибыль) | 753,50 ₽ | 789,00 ₽ | +35,50 ₽ |

Безубыточность ПВЗ: **39 оп/день** при доле mesh 30% и мощности 120 оп/день.

## 4. Ограничения и заглушки (честно)

- **Хаб и магистраль** — параметры модели (`hub_handling_rub`, `trunk_cost_per_order_rub`), не реальный перевозчик.
- **Платёжный шлюз** не реализован — все расчёты в ledger, реальных денег нет.
- **Клиентское приложение** не реализовано — есть карточка покупателя по токену (`/track/{token}`).
- **Аутентификация** — статические API-ключи, не OAuth/JWT.
- **Масштаб** — SQLite, один процесс API. План перехода на PostgreSQL+Redis — в `docs/SCALE.md`.

## 5. Быстрые команды для показа

```bash
# Сброс БД + пересборка
docker compose down -v && docker compose up -d --build

# Демо-сценарии
python3 scripts/demo.py

# Все тесты
cd api && DATABASE_URL=sqlite:////tmp/mesh-pytest.db ../.venv/bin/python -m pytest tests -q
cd .. && .venv/bin/python -m pytest economics/tests -q

# Сценарий «что если» (меняем бонус ПВЗ)
curl 'localhost:8000/api/v1/economics/scenario?mesh_bonus=5'

# Скоринг размещения
curl -X POST localhost:8000/api/v1/catalog/placement-score \
  -H 'X-API-Key: demo-seller-key' \
  -H 'Content-Type: application/json' \
  -d '{"sku":"TEST-001","qty":5,"cell_size":2,"demand_per_day":3,"city":"Казань"}'

# Здоровье
curl localhost:8000/api/v1/health/deep
```
