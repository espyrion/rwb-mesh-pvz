## 1. Репозиторий и структура

```
mesh-pvz/
├── api/            FastAPI + SQLAlchemy: заказы, маршруты, ledger, аудит, симуляция часов
├── web/            vanilla JS без сборщиков: кабинет ПВЗ/продавца, экономика, демо, карта
├── economics/      params.yaml, модель четырёх сторон, сценарии, генератор ECON_REPORT
├── scripts/        demo.py, simulate.py, gen_openapi.py, run_tests.sh
├── docs/           отчёты, API, red team, пилот, submission, openapi.json
├── .github/        CI: api, economics, web-lint, contract, simulation-smoke
└── docker-compose.yml, docker-compose.dev.yml
```

Актуальная ветка — `master`: все рабочие ветки влиты, последний merge — из
`fix/final-review-and-ui-polish`. Конкурсная версия зафиксирована тегом `submission-2026-11-25` в
репозитории https://github.com/espyrion/rwb-mesh-pvz (хеш тега — `git rev-parse submission-2026-11-25`).

Поставка — архив тега либо сборка из чистого клона: `git archive --format=tar.gz -o mesh-pvz.tar.gz
submission-2026-11-25` (дальше распаковать и, при желании, `docker compose build`), либо
`git clone https://github.com/espyrion/rwb-mesh-pvz && cd rwb-mesh-pvz && git checkout submission-2026-11-25
&& docker compose build`. В архиве только исходники: база, тома и образы в поставку не входят.

## 2. Как поднять с нуля

Нужен Docker с compose. Внешняя сеть и внешние сервисы не требуются: SQLite, seed при старте.

```bash
# production: всё внутри образов
docker compose up -d --build

# dev: api с --reload, web/src смонтирован
docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d --build

# проверка
curl http://localhost:8000/health
curl http://localhost:8000/api/v1/health/deep
```

* UI — http://localhost:5173
* Swagger — http://localhost:8000/docs
* Сброс данных — `docker compose down -v && docker compose up -d --build`

**Обязательно:** после правок `api/` или `web/src` пересобрать образ
(`docker compose up -d --build`). В production-режиме исходники запечены в образ, без пересборки
на :8000/:5173 останется старый код.

Демо-ключи и роли — в `README.md`, раздел «Роли и ключи API». Секретов и платёжных данных в
репозитории нет.

## 4. Ключевые числа

Эталон: товар 2 500 ₽, 1,5 ячейки, 3 дня хранения.

| Сторона | hub | mesh | Δ |
|---|---:|---:|---:|
| ПВЗ | 27,50 ₽ | 42,50 ₽ | +15,00 ₽ |
| Маркетплейс | 358,50 ₽ | 359,00 ₽ | +0,50 ₽ |
| Продавец | 367,50 ₽ | 367,50 ₽ | 0,00 ₽ |
| Цепочка | 753,50 ₽ | 769,00 ₽ | +15,50 ₽ |
| Покупатель | 2 659,00 ₽ | 2 629,00 ₽ | −30,00 ₽ (−1,13%) |
| Срок | 30 ч | 3 ч | −27 ч |

* Межгород: цепочка 753,50 → 758,50 ₽, маркетплейс 358,50 → 348,50 ₽, срок 30 → 3 ч.
* Безубыточность ПВЗ: 38 операций/день при базовой доле дня ПВЗ 30% (`pvz_day_mesh_share_pct`); при доле локальных пар 62% — 33 операции/день (диапазон 41–32 при 15–70%).
* Очередь M/M/1: 80% → 0,80 ч, 85% → 1,13 ч, 95% → 3,80 ч; цель 80%, алерт 85%.
* Симуляция 2000 заказов, seed 42: наивный mesh — 2000 опозданий, пик 226%, потери 701 623,38 ₽,
  107,15 ₽/заказ, маржа 5,75%; адаптивный overflow — 953 опоздания, 136%, 351 902,12 ₽,
  124,12 ₽/заказ, маржа 10,00%. На 100/500 заказах режимы совпадают (перелив выше 960/день).

Источник — `economics/params.yaml` и генераторы `economics/report.py`, `scripts/simulate.py`;
провенанс каждого числа — `docs/PROVENANCE.md`.

## 6. Что проверяет CI

`.github/workflows/ci.yml`, все джобы на SQLite, без Docker и внешних API. Тесты всегда работают на
своей временной базе: `api/tests/conftest.py` сам выставляет `DATABASE_URL` на свежий каталог в
`tempfile.mkdtemp()` и создаёт его при импорте, поэтому отдельная база в CI не задаётся и боевой том
не затрагивается ни в CI, ни локально:

| Job | Проверка |
|---|---|
| `api` (py3.11, 3.12) | `cd api && python -m pytest tests -q --tb=short`, 143 теста |
| `economics` | `python -m pytest economics/tests -q --tb=short`, 28 тестов |
| `web-lint` | `node --check web/src/*.js` |
| `contract` | перегенерация OpenAPI в `/tmp` и сравнение распарсенного JSON с `docs/openapi.json` |
| `simulation-smoke` | `simulate.py --orders 100 --seed 42` + перегенерация `SCALE.md` и diff |

Локально те же команды: `cd api && ../.venv/bin/python -m pytest tests -q` (из корня `pytest api/tests`
падает: `api/pytest.ini` задаёт `pythonpath = ..`, а тесты ждут рабочего каталога `api/`) и
`.venv/bin/python -m pytest economics/tests -q`. Всё сразу — `bash scripts/run_tests.sh`: он же проверяет,
что `docs/ECON_REPORT.md` и `docs/openapi.json` не устарели (артефакты не перезаписывает).

## 7. Известные ограничения и риски

Из `docs/REDTEAM.md`:

* **Данные и допущения.** Тарифы, бонусы, штрафы и SLA — параметры модели, а не обязательства RWB.
  Хаб, магистраль и платёжный шлюз — помеченные заглушки; реальные деньги не двигаются.
* **Спрос и ёмкость.** Модель не учитывает сезонность, промо и межгородские волны; при 2000
  заказов/день сеть работает выше потолка 960, поэтому 953 опоздания и потери 351 902,12 ₽ —
  это цена перелива, а не «нулевой» сценарий.
* **Экономика.** Маржа маркетплейса на mesh-заказе +0,50 ₽ — тонкая; при росте логистики на
  0,50 ₽ преимущество исчезает. Бонус ПВЗ 15 ₽ — рычаг: при 5 ₽ прибыль ПВЗ падает с 42,50 до
  32,50 ₽, порог безубыточности растёт с 38 до 42 операций/день.
* **Хранение.** Продавец платит 5 ₽/ячейку/день; на 52-й день хранение обнуляет его прибыль.
  Продукт реагирует раньше — на 21 день или 600 ₽ начисленного хранения.
* **Конкурентность.** Защита от гонок реализована транзакциями и CAS-обновлением строк;
  в SQLite при высокой параллельной записи возможны `database is locked` — для пилота нужен
  PostgreSQL (вне MVP).
* **Масштаб.** Один город и 8 точек; федеральная сеть требует партиционирования, фоновых
  воркеров и отдельного сервиса маршрутизации.

## 8. Что не входит в MVP

* реальная интеграция с RWB, платёжным шлюзом и трекингом перевозчика;
* авторизация пользователей (только роли по API-ключам), 2FA, аудит действий операторов;
* PostgreSQL, Redis, очереди, горизонтальное масштабирование;
* мобильное приложение покупателя и push-уведомления;
* юридически значимый ЭДО, фискализация, возвраты денег покупателю;
* ML-прогноз спроса: сейчас спрос наблюдается по истории заказов и закону Литтла;
* production-мониторинг, алертинг и SLO-дашборды (есть `/health/deep` и инциденты).
